# AI Document Assistant

An AI-powered document question-answering application built with Python and FastAPI.

Upload a PDF, ask questions about its content, and receive natural-language answers generated by a local Large Language Model (LLM).

The application uses **Retrieval-Augmented Generation (RAG)** to find relevant information from documents using semantic search and generate answers using mistral  through Ollama.

## Features

- Upload PDF documents through a REST API.
- Extract text from PDFs using PyMuPDF.
- Split extracted text into smaller, overlapping chunks.
- Generate text embeddings using `nomic-embed-text`.
- Perform semantic search using cosine similarity.
- Rank document chunks by relevance to a question.
- Retrieve the three highest-scoring chunks as context.
- Apply a similarity threshold to filter potentially irrelevant questions.
- Generate natural-language answers using mistral:latest through Ollama.
- Validate API requests using Pydantic.
- Handle invalid PDFs, empty PDFs, and missing documents.
- Explore API endpoints using Swagger UI.
- Run automated tests using pytest.
- Keep document processing and language model inference local.

## How It Works

The application follows a basic Retrieval-Augmented Generation (RAG) pipeline.

1. Upload a PDF document through the API.
2. Extract text from the PDF using PyMuPDF.
3. Split the extracted text into overlapping chunks.
4. Generate an embedding for each chunk using `nomic-embed-text`.
5. Store the chunks and their embeddings in memory.
6. Submit a question about the document.
7. Generate an embedding for the question.
8. Calculate cosine similarity between the question embedding and each document chunk embedding.
9. Rank the chunks by similarity score.
10. Check whether the highest similarity score meets the relevance threshold.
11. Select the three highest-scoring chunks.
12. Send the retrieved context and question to mistral:latest through Ollama.
13. Return the generated answer as a JSON response.

If the question is considered irrelevant, the application returns a fallback response instead of generating an answer.

## Installation and Setup

### 1. Clone the Repository

```bash
git clone https://github.com/uday-Tharlada-0/AI_DOCUMENT_ASSISTANT.git

cd AI_DOCUMENT_ASSISTANT
```

### 2. Install Dependencies

Install the project's dependencies using `uv`:

```bash
uv sync
```

### 3. Download the Required Models

Download mistral:latest:

```bash
ollama pull mistral:latest
```

Download the embedding model:

```bash
ollama pull nomic-embed-text
```

Verify the installed models:

```bash
ollama list
```

### 4. Configure Ollama

Ensure the Ollama server is running and accessible from the environment where FastAPI runs.

The application uses two Ollama API endpoints.

**Text generation:**

```text
http://<ollama-host>:11434/api/generate
```

**Text embeddings:**

```text
http://<ollama-host>:11434/api/embed
```

The endpoints can be configured using environment variables:

```bash
export OLLAMA_URL="http://<ollama-host>:11434/api/generate"

export OLLAMA_EMBED_URL="http://<ollama-host>:11434/api/embed"
```

Replace `<ollama-host>` with the hostname or IP address accessible from your application environment.

These commands are for Linux and macOS shells. Configure equivalent environment variables in other operating systems as needed.

**Windows and WSL note:** If FastAPI runs inside WSL while Ollama runs on Windows, ensure Ollama is reachable from WSL. Use the appropriate Windows host address rather than assuming that `127.0.0.1` will work.

Keep the Ollama API accessible only to trusted systems. Avoid exposing it directly to the public internet.

### 5. Start the FastAPI Application

If `main.py` is in the project root, run:

```bash
uv run uvicorn main:app --reload
```

The `--reload` option automatically restarts the development server when code changes.

### 6. Open Swagger UI

Once the application starts, open:

http://127.0.0.1:8000/docs

Use the interactive API documentation to upload a PDF and ask questions about its contents.

### 1. Check Application Status

### 2. Upload a PDF

**Endpoint:** `POST /upload`

Upload a PDF using the file upload field in Swagger UI.

The application:

1. Validates the uploaded file.
2. Extracts text using PyMuPDF.
3. Rejects PDFs without extractable text.
4. Splits the text into overlapping chunks.
5. Generates an embedding for each chunk.
6. Stores the chunks and embeddings in memory.

An illustrative response may look like this:

```json
{
  "filename": "Python and Java Study Notes.pdf",
  "pages": 10,
  "message": "File uploaded and text extracted successfully."
}
```

The filename and page count are examples. Actual response fields and values depend on the implementation and uploaded document.

### 3. Ask a Question

**Endpoint:** `POST /ask`

Submit a question about a PDF that has already been uploaded.

Example request:

```json
{
  "filename": "Python and Java Study Notes.pdf",
  "question": "Explain high-level programming languages."
}
```

The filename must match a document uploaded to the currently running application.

An illustrative response for a relevant question:

```json
{
  "question": "Explain high-level programming languages.",
  "answer": "A high-level programming language provides abstractions that make programming easier to understand and write."
}
```

The answer above is an example, not a guaranteed response.

If the question is considered irrelevant to the document, the application returns a fallback message:

```json
{
  "question": "What is the capital of France?",
  "answer": "I couldn't find relevant information in this document."
}
```

Actual responses depend on the API implementation, uploaded document, similarity scores, and language model output.

## Understanding Semantic Search

Semantic search attempts to identify text that is conceptually related to a question rather than relying only on exact keyword matches.

The application uses embeddings to represent text as numerical vectors.

For each question:

1. Generate an embedding for the question.
2. Compare it with stored document chunk embeddings.
3. Calculate cosine similarity.
4. Rank chunks by their scores.
5. Retrieve the highest-scoring chunks.

### What Is Cosine Similarity?

Cosine similarity measures the relationship between two vectors based on the angle between them.

In this application, it helps rank document chunks according to their relationship with the question.

**Important points:**

- Higher scores generally indicate greater similarity between the embeddings.
- Similarity scores are not percentages.
- A high score does not guarantee that a chunk contains the correct answer.
- A relevance threshold is a heuristic, not a guarantee that a question is answerable.
- Retrieval quality depends on the embedding model, document content, and chunking strategy.

The current application uses a threshold of `0.45` to reject questions whose best-scoring chunk falls below that value.

This threshold may need adjustment after testing with representative documents and questions.

## Text Chunking

The application divides extracted text into smaller pieces before generating embeddings.

The current configuration uses:

- **Chunk size:** 500 characters
- **Overlap:** 100 characters

The overlap preserves some context between consecutive chunks.

For example, when one chunk ends with a sentence fragment, the next chunk may contain part of the same text.

The current implementation uses fixed-size character-based chunking. It does not guarantee that chunks end at sentence or paragraph boundaries.

## Current Limitations

- Uploaded documents and embeddings are stored in memory and are lost when the application restarts.
- Documents must be uploaded again after a restart.
- Fixed-size chunking can split sentences and words.
- The similarity threshold cannot guarantee that a question is answerable from the document.
- The language model may generate unsupported information despite receiving retrieved context.
- Scanned PDFs without extractable text may require OCR.
- Persistent document storage has not yet been implemented.
- Authentication and authorization have not yet been implemented.
- A dedicated frontend has not yet been implemented.
- Ollama must be reachable from the environment running FastAPI.
- Automated tests do not guarantee that every possible input or failure case is handled.
